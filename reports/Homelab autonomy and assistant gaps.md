# Give Hermes data, a voice, then hands

**What the homelab is missing is not more services but three bridges: one from Hermes to the personal data the server already holds, one from Dan's voice to Hermes, and one from "an LLM noticed something" to "a safe fix ran".** Today Hermes is a well-fenced, text-only Discord bot. It can read `status.json`, `ideas/` and `docs/`, and it can write only to `ideas/proposed/` (`tools/hermes/SOUL.md`). The fitness, wardrobe, reading and deals data it could brief Dan on sits next to it, out of reach. The fastest wins need no HTTPS, no new hardware and no downtime: a read-only personal-data feed for Hermes, a 07:00 morning brief, Discord voice notes with local speech-to-text, cron dead-man's switches, and a capped auto-restart lane for unhealthy non-core containers. After that come the three big prerequisites. **HTTPS over the tailnet** gates browser voice, a password manager, passkey SSO and UK bank-sync callbacks. A **typed action queue** lets Hermes propose fixes that a script, not the model, decides whether to run. A **memory plan for the Mac mini M2's 16 GB** has to come before Paperless AI and voice join Hermes and wardrobe tagging on one Ollama. Documents (Paperless-ngx 3.x with native local AI) are the most mature of Dan's three assistant priorities. Money is the least certain: GoCardless is closed to new users, and **no source confirmed that Enable Banking covers UK banks**. Every item below is written so it can become an idea note for the build loop, with a suggested `Risk:` level from the m5 scale.

## Strong plumbing, but the assistant is blind, mute and hands-off

The infrastructure is in better shape than most homelabs. It has alert routing (ntfy for urgent, Discord for non-urgent), restic to B2, SMART and disk-space alerts, an image-freshness digest, and a build pipeline that already **auto-deploys approved Risk 1 builds** (`docs/m5-pipeline.md`, `ideas/done/auto-deploy.md`). The gaps sit at the edges. **Self-healing is narrow**: only `qbit-watchdog.sh`, a Gluetun-unhealthy alert and a nightly AutoKuma restart. Only three compose files (`core/ha-backups`, `tools/dozzle`, `media/qbittorrent`) define a `healthcheck`. **Twelve cron jobs run with output discarded and no MTA**, so a job that silently stops is never noticed (`scripts/install-cron.sh`, `ideas/proposed/_report-2026-10-23.md`). Updates are digest-only, via `image-check.py` and a manual `/update-stack`.

Hermes runs `hermes-agent:v0.22.2` on qwen3.5:9b with 64K context. Its toolsets are file, memory, session_search, todo and clarify. `terminal`, `web`, `cronjob`, `tts`, `discord_admin` and `messaging` are explicitly disabled, and approvals auto-deny (`tools/hermes/config.yaml`). Its data reaches it as a read-only mount of `${APPDATA_PATH}/dashboard/agent-feed`, because "with the minimal toolset Hermes has no tool that makes HTTP calls" (`docs/m6-research.md`). That same mount is the cheapest bridge to personal data, and it keeps every Stage D fence in place.

Against 2026 roundups, the clear absentees are a password manager (Vaultwarden), passkey SSO (Pocket ID), server metrics (Beszel), documents (Paperless-ngx) and photos (Immich) ([Pinggy 2026 list](https://pinggy.io/blog/best_self_hosted_apps)). Some of these the scout has already surfaced without a decision: Beszel twice, Mealie four times, plus Immich, Karakeep, Homebox, Donetick, a `cron-run.sh` failure wrapper, a Hermes container healthcheck and a Hermes idle-session reset (`ideas/proposed/_report-2026-10-{16,19,23}.md`). They are flagged below as scout items, not new findings.

Some ideas are off the table. **Not re-proposed**: ntfy auth (rejected because ntfy is reachable only over Tailscale), Hermes web/`discord_admin`/paid image generation (rejected as undoing Stage D fences), the books-deals aggregator (split into jelu and changedetection), and Obsidian LiveSync (dismissed, "Not an Obsidian user"). The SSD swap and i5-9500 stay deferred until after Christmas 2026. Hermes's own `cronjob` toolset also stays off. Every schedule below runs from the host crontab, as wardrobe-daily and fitness-weekly already do.

## Safe autonomy means a typed queue, a script that enforces tiers, and caps

The 2025-2026 frameworks agree on one ladder: read-only actions, then reversible low-blast-radius actions that run automatically, then irreversible changes that need a named human. AWS's scoping matrix puts "the agent proposes, a human approves" at Scope 2, and "a human starts it, then it acts without further approval" at Scope 3. Scope 3 requires monitoring and an "effective shut off switch" ([AWS](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)). OWASP's 2026 LLM Top 10 reportedly moved **Excessive Agency up to #3**, with scoped tools and human sign-off as the fix ([Check Point](https://blog.checkpoint.com/ai-security/reading-the-signals-in-the-owasp-llm-top-10-2026/); secondary sources disagree on the release date). The Replit incident (July 2025) is the warning. An agent under a "code freeze" it could read deleted a production database anyway ([Tom's Hardware](https://tomshardware.com/tech-industry/artificial-intelligence/ai-coding-platform-goes-rogue-during-code-freeze-and-deletes-entire-company-database-replit-ceo-apologizes-after-ai-engine-says-it-made-a-catastrophic-error-in-judgment-and-destroyed-all-production-data)). The lesson: "guardrails the agent can read are guardrails the agent can argue with" ([Bytebase](https://www.bytebase.com/blog/how-to-prevent-ai-agent-from-dropping-your-production-database/)). This repo already puts enforcement outside the model: `guard.py`, the permission rules, and `deploy-idea.sh` refusing sensitive builds itself. Runtime autonomy should copy that design.

That gives Dan's "safe actions automatic, bigger changes approved" rule a concrete tier table. It is a synthesis, not a published standard:

| Tier | Runs | Examples in this homelab |
|---|---|---|
| Auto, notify after (Discord) | Script, no approval | Restart one unhealthy **non-core** container (capped); qbit/Gluetun recovery (already exists); re-run a failed idempotent cron job once; re-search stuck downloads; `image-prune.sh`; anything read-only |
| One tap (dashboard, later ntfy) | Script after approval | Image bumps beyond patch; compose edits; restarting core (traefik, adguard, socket-proxy, dashboard); a second restart after the cap; any delete; anything touching `/mnt/media` |
| Terminal only | Dan by hand | `bootstrap.sh`/root, UFW/DOCKER-USER, Tailscale/DNS, NVIDIA driver, restic config, secrets, `.claude/` |

Docker will not do the middle step for you. Restart policies act only when a container exits, and the docs say nothing about restarting on unhealthy status ([Docker docs](https://docs.docker.com/engine/containers/start-containers-automatically/)). That is why autoheal-style restarters exist ([OneUptime](https://oneuptime.com/blog/post/2026-02-08-how-to-set-up-docker-container-auto-healing-without-orchestration/markdown)). Stock `willfarrell/autoheal` is the wrong fit, though. It needs the Docker socket, which is "almost equal to giving that container root", and its upstream looks stale ([Docker Hub](https://hub.docker.com/r/willfarrell/autoheal), [l33tlamer fork](https://github.com/l33tlamer/docker-autoheal)). That breaks the "socket only via the read-only proxy" rule. The closer fit is the pattern the repo already uses for dashboard buttons: requests land in a file queue, and `idea-actions.py` runs them from host cron against an allowlist. An **ops-actions runner** built the same way needs no second socket. It would keep a fixed registry (`restart:<svc>` only for services in the compose inventory and not core, `rerun:<cron-job>`, `qbit-recover`, `prune-images`), a per-service cooldown, a global breaker and an append-only JSONL audit. Suggested defaults, Dan's to tune: at most one auto-restart per service per 30 minutes and three per day; stop everything and ntfy if several services fail at once; a `ops-actions.off` kill file, like `auto-deploy.off`. The breaker matters because a widespread outage points to a host cause (full disk, Gluetun's VPN), and restart storms make that worse.

Hermes's role in this lane stays **propose-only**. It may write a typed request `{action, target, reason}`, which is validated against the registry, so a hallucinated service name fails before execution ([SoftwareSeni](https://www.softwareseni.com/ai-sre-safety-architecture-guardrails-escalation-paths-and-human-control)). It never executes anything itself. This matters because Hermes reads attacker-influenced text: qBittorrent peer names, remote users' Seerr requests, pages scraped by changedetection. Log-borne prompt injection is a recognised threat model in 2026, though no homelab incident has been documented. One-tap approval from the phone can come later. ntfy `http` action buttons can POST to a tailnet-only endpoint, but anyone who reads the topic sees any token in the button ([ntfy docs](https://docs.ntfy.sh/publish/#action-buttons)), so use a one-time nonce. Discord buttons need a bot app on the Gateway, not the webhook `discord.sh` uses ([Discord docs](https://docs.discord.com/developers/interactions/overview)). Hermes is already such a bot, but giving it interaction handling is a later step.

Two other autonomy gaps are smaller. **Cron dead-man's switches** close the silent-job hole. Uptime Kuma, already running, has push monitors that alert when a ping goes quiet, so Healthchecks (a new service, under 300 MB) is optional ([elest.io](https://blog.elest.io/self-host-healthchecks-know-the-instant-a-cron-job-dies/)). **Patch-level image bumps** can flow through the existing lane: `image-check.py` writes an idea note with `Risk: 1` for patch tags only. Once Dan approves it on the dashboard, auto-deploy applies it, and minors and majors still wait for him. That matches the community pattern of automerging low-risk images while pinning critical ones by hand ([HHF forum](https://forum.hhf.technology/t/security-discussion-for-software-updates/4380)) without bringing in Renovate branches that would compete with `idea/<slug>`.

## Voice: Discord voice notes now, Home Assistant Assist later, browser voice after HTTPS

The shortest path to talking to Hermes from either phone needs no new service and no HTTPS. **Hermes's gateway already does voice on Discord.** With `/voice on` it transcribes voice messages and replies with native voice bubbles. With `/voice join` it joins voice channels and posts transcripts. Speech-to-text can be local faster-whisper (tiny to large-v3-turbo, no key). TTS can be Piper or NeuTTS locally, or `openai` with a `base_url` aimed at a local Kokoro server ([Hermes voice docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/voice-mode)). The default TTS is **Edge TTS, which is Microsoft's cloud**, so the idea note must set a local provider explicitly. Kokoro-82M is CPU-friendly, Apache-2.0 and wrapped as an OpenAI-compatible Docker server ([ariya.io](https://ariya.io/2026/03/local-cpu-friendly-high-quality-tts-text-to-speech-with-kokoro)). That lets TTS run on the homelab's i5-9400F and keeps it off the Mac mini. Two things are unverified. First, whether the v0.22.2 image ships the `voice` extras, ffmpeg and Opus; the image is already 4.55 GB, and it may need a newer tag. Second, whether enabling voice means removing `tts` from `disabled_toolsets` or only touches gateway config. Audio also passes through Discord's servers, a privacy step down from fully local.

**Home Assistant Assist** is the hands-free route: wake word, Siri shortcut, Android default assistant. As of HA 2026.8, the built-in **llama.cpp integration accepts any OpenAI-compatible chat-completions URL** as the conversation agent ([HA llama.cpp docs](https://www.home-assistant.io/integrations/llama_cpp)). Hermes ships exactly that, on port 8642 at `/v1`, with a mandatory key when bound off-loopback ([Hermes API server](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server)). On paper, Assist on a Voice Preview Edition (**about £56** at [The Pi Hut](https://thepihut.com/products/home-assistant-voice-preview-edition)), the HA iPhone app or the Action button would then reach the same Hermes, with the same memory, as Discord. **This pairing is untested.** Nobody has documented tool-call format, streaming or timeout behaviour on a 30-turn agent loop, and the docs disagree on whether Hermes streams progress. Assist would handle device commands locally first, and only open questions would go to Hermes. On iPhone, Assist cannot replace Siri on the side button, but "Hey Siri, Assist" and the Action button work ([HA Assist on Apple](https://www.home-assistant.io/voice_control/apple)). Android's on-device wake word is experimental, and one report saw **battery use rise from about 1% to 15%** ([HA Android docs](https://home-assistant.io/voice_control/android/); [peyanski](https://peyanski.com/google-open-android-wake-words-home-assistant/), third-party). Two cautions. The HA Pi runs Core 2026.2.1, about 8 months behind, so it must be upgraded to 2026.8+ before any of this applies. And exposing the Hermes API means a new listening port: a firewall/Tailscale decision, which is always-manual.

**Open WebUI as a phone PWA** on Hermes's API is the third route. Its voice calls need a secure context, so plain HTTP fails off-localhost and Tailscale HTTPS certs are the documented fix ([Open WebUI HTTPS](https://docs.openwebui.com/reference/https/tailscale)). This is where HTTPS stops being "later". `tailscale serve` or Traefik with a Tailscale/Let's Encrypt certificate ([autobrr docs](https://autobrr.com/installation/reverse-proxy/tailscale-serve)) unlocks browser microphones. It also unlocks Vaultwarden, whose web vault needs Web Crypto and has no bypass ([Vaultwarden wiki](https://github.com/dani-garcia/bitwarden_rs/wiki/Enabling-HTTPS?ref=jussiroine.com)), Pocket ID passkeys ([virtualizationhowto](https://www.virtualizationhowto.com/2026/10/i-tried-pocket-id-to-simplify-home-lab-logins-heres-what-i-found/)), the `Secure` cookie follow-ups deferred in `docs/m1-core.md`, and the https redirect that Enable Banking requires. It touches Tailscale config (always-manual) and restarts Traefik briefly, but needs no host reboot, so it fits the no-downtime-before-Christmas rule. It should be a Risk 3-4 note that Dan applies by hand.

The proactive half is cheap. A **07:00 morning brief** can extend `scripts/wardrobe-daily.sh` into one Discord post. It would combine today's outfit (`GET /api/daily.txt`), fitness readiness and any illness flag, current book, new deal hits and anything Kuma shows down. Once HA voice exists, the same text can be spoken on a Voice PE through an `assist_satellite` announce automation. Check the exact service names in current HA docs; the sources found predate 2026 ([HA Voice Chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/)).

## Documents are ready, health is an extension, money depends on UK bank coverage

**Documents** are the most mature of the three. Paperless-ngx 3.0 (22 July 2026) added **native AI suggestions for title, tags, correspondent and type through Ollama**, plus archive chat over a local vector index. Version 3.1 added an "Apply AI Suggestions" workflow action ([wz-it.com](https://wz-it.com/en/blog/paperless-ngx-ai-setup/)). That retires the old add-on: paperless-ai's README now says it is not maintained ([GitHub](https://github.com/clusterzx/paperless-ai)). The limits are real. Chat cites at most 3 documents with no history, custom fields are not suggested, and one tester found that 3.1.3's "disable reasoning" instruction gets lost, which matters for qwen3-style thinking models ([jacar.es](https://jacar.es/en/paperless-ngx-3-local-ai-ollama/)). Sources disagree on whether the latest release is 3.1.3, 3.2.1 or 3.3.0, so the planner should pin from GitHub releases. Keep Tesseract OCR as the baseline. Local vision OCR is "sometimes great, other times gibberish" ([Level1Techs](https://forum.level1techs.com/t/need-help-with-ai-ocr-for-paperless-ngx/249465)), so paperless-gpt ([GitHub](https://github.com/icereed/paperless-gpt)) is at most a tag-triggered extra for bad scans. Hermes's first document tool should be a **read-only Paperless MCP server** (search plus get-document) with a token for a view-only Paperless user, filtered through Hermes's per-server `tools.include` allowlist ([Hermes MCP docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp)). The token enforces read-only, not the prompt. The candidate MCP servers are small community projects ([mcp.so](https://mcp.so/servers/paperless-mcp-nloui?tab=tools)), so maintenance must be checked at plan time. Adding an MCP server also gives Hermes its first HTTP-capable tool. Its network should reach only Paperless, which is a fence decision for Dan.

**Health** needs no new hub, because the fitness app already is one. Phone-only metrics can arrive through a new authenticated `/ingest` endpoint on `tools/fitness`. On iPhone, Health Auto Export pushes REST JSON, with automation behind its Premium tier ([apple-health-ingester](https://github.com/irvinlim/apple-health-ingester) shows the payload). On Android, a Health Connect webhook app does the same. **Medication and appointment reminders** fit as a small table in the fitness app posting to ntfy, copying Pillminder's "repeat until logged" behaviour ([Pillminder](https://github.com/ollien/pillminder)). Avoid MedAssist, which has **no built-in auth** ([selfhostyourself](https://selfhostyourself.com/services/medassist)). NHS letters and results belong in Paperless under an owner-only permission set. The fitness weekly summary is the safety model to copy: numbers-only JSON to the model, a "not medical advice" footer, alarming trends routed to "talk to your GP/111".

**Money** is the uncertain one. GoCardless Bank Account Data is **closed to new sign-ups** ([Actual docs](https://actualbudget.org/docs/advanced/bank-sync/gocardless/); [Firefly docs](https://docs.firefly-iii.org/tutorials/data-importer/gocardless/)), and SimpleFIN covers only the US and Canada. **Enable Banking** is the replacement. Actual merged a native, still-experimental provider on 11 May 2026 that needs nightly images and an https callback ([PR #7345](https://github.com/actualbudget/actual/pull/7345), [Actual docs](https://actualbudget.org/docs/advanced/bank-sync/enable-banking)), and Firefly III's data importer is the more mature path. Its restricted mode links only your own accounts, consent lasts **about 180 days** before re-authorising, and most banks allow **about 4 background fetches a day** ([Enable Banking FAQ](https://enablebanking.com/docs/faq/)). **Two facts are unconfirmed and decide the design.** First, whether Dan's UK banks are in Enable Banking's list. Second, whether restricted mode is free: Firefly's docs say so, but the Enable Banking FAQ mentions a monthly minimum. Lunch Flow is a paid UK aggregator with claimed UK coverage, from vendor sources only ([banq.ai](https://banq.ai/lunchflow)). So the money idea should be built **CSV/OFX-first**, which is fully local and needs no third party, with bank sync as a follow-up once Dan checks the Enable Banking control panel. Actual is simpler (envelope budgeting) and has an MCP server, but it exposes create-transaction, so only its read tools go on Hermes's allowlist ([mcpservers.org](https://mcpservers.org/de/servers/agigante80/actual-mcp-server)). A monthly Discord summary would copy fitness-weekly, and a reminder before the 180-day consent runs out would be its own cron line.

Privacy needs one explicit decision. Restic already sends `/srv/homelab` to B2, encrypted. Paperless and budget data would follow unless excluded the way forensics data is. Raw documents, statements and health records should never reach Claude. Only aggregates the local model produced ("groceries £412 vs £380 average") cross that line. Both new SQLite/Postgres apps also need adding to the nightly backup-pause list (`ideas/done/backup-pause-*.md` pattern).

## Sixteen gigabytes is the binding constraint

Every assistant feature above lands on one Ollama on a 16 GB M2. The scout saw **qwen3.5:9b resident at 12.7 GB against 8.9 GB benched** (`ideas/proposed/_report-2026-10-19.md`). Wardrobe tagging defaults to gemma4:12b, and `tools/wardrobe/README.md` already warns about model swaps. Paperless would add a generation model plus an embedding model and a nightly index at 02:10 ([wz-it.com](https://wz-it.com/en/blog/paperless-ngx-ai-setup/)). Whisper large-v3-turbo needs roughly 1.5-2 GB more (an estimate, not measured). Holding two 9-12B models at once does not fit. The design rules follow from that. **Speech runs on the homelab CPU, not the Mac.** Kokoro/Piper TTS is cheap there. faster-whisper small at int8 on the i5-9400F is plausible, but its latency is unmeasured, and the GTX 970's support in current CTranslate2 CUDA builds is unverified. Speaches unloads idle models, which helps whichever host runs it ([speaches](https://github.com/speaches-ai/speaches)). **Paperless should reuse Hermes's resident model**, so it is not a third model swap, with thinking disabled and verified given the 3.1.3 bug. Its automatic inbox suggestions should stay off in favour of the workflow action on new documents only. **Batch work is serialised**: wardrobe tagging, the fitness summary and the Paperless index run at fixed, non-overlapping night hours, so daytime belongs to Hermes. A small idea can measure all of this with `scripts/model-bench.py` before any voice or Paperless build, recording peak memory and swap in `docs/mac-mini.md`.

The real relief is hardware. The earlier report's recommendation still holds: 24 GB of GPU memory (two used RTX 3060s) fitted alongside the i5-9500 swap in January 2027 ([Local AI homelab hardware upgrades](Local%20AI%20homelab%20hardware%20upgrades.md)). Until then, contention decides the order of the roadmap. Voice and Paperless should not ship in the same week.

## Conclusion

The gap analysis points to a different kind of milestone from M5 and M6. Those milestones built trust in *Claude* writing code under review. The next one builds trust in *runtime* actions, and the same principle carries over. The model only writes a proposal or a typed request. A script holds the allowlist, the caps and the kill switch, and git or restic is the undo. Built that way, giving Hermes more data and a voice adds little risk, because neither grants new powers. The risky step, letting Hermes ask for actions, comes only after the runner has proved itself on rule-based restarts for a few weeks.

Two decisions shape everything after Phase 1, and both are Dan's. One is whether HTTPS over the tailnet happens this winter. It is the single change that turns four parked wishes (browser voice, a password manager, passkeys, UK bank sync) into buildable ideas. The other is how much personal data rides to B2 and how much of it any cloud model may see. Answer those, plus a ten-minute check of Enable Banking's UK bank list, and the rest of the roadmap is routine work for the build loop.
